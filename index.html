Tickera — Engineering Depth
Testing Strategy  ·  Observability  ·  Saga Compensation  ·  Event Sourcing
Testing Strategy
  • Unit (Axon given/when/then) — aggregate invariants and state transitions verified without Spring context or infrastructure. BookingAggregateTest, PaymentAggregateTest.
  • Contract (Pact V3 async CDC) — booking-service publishes a consumer pact for BookingConfirmed; payment-service verifies it as provider. Committed pact files caught schema drift before integration.
  • Integration (Testcontainers) — real Kafka + PostgreSQL spun per test run: confirms command → event → projection chain and that the integration event physically lands on the topic.
  • CI structure — three parallel jobs fan out after a compile gate, then SonarQube aggregates all JaCoCo reports.
Observability Dashboard
  • HTTP Traffic row — request rate (req/s), p95 latency (s), 5xx error rate per service.
  • Booking Funnel row — Micrometer counters tracking CREATED → CONFIRMED → PAID / CANCELLED state transitions; Redis idempotency guard counter (first-delivery vs. duplicates blocked).
  • Infrastructure row — Kafka consumer record rate, JVM heap, GC pause rate.
  • $service variable — single Grafana template variable filters all panels to one service or shows aggregate view.
Key Engineering Decisions
  • Axon over plain Kafka consumers — Axon's aggregate pattern enforces command validation and event replay before a single line of Kafka consumer code exists; gives free event-sourced audit history.
  • Database-per-service — each service owns its schema; cross-service joins go through Kafka events, not SQL. Enables independent schema evolution and deployment.
  • Redis SETNX for idempotency — Kafka's at-least-once guarantee means payment-service may receive BookingConfirmed twice. SETNX paymentId ensures only the first delivery charges the card.
  • Saga with Axon deadline — if PaymentCompleted never arrives within 15 minutes (e.g., payment-service down), the deadline handler fires a compensating CancelBooking command — preventing stuck bookings from holding inventory indefinitely.
  • Dead-Letter Topics + ExponentialBackOff — transient failures retry with back-off; permanently failed events route to a DLT for manual inspection rather than blocking the partition.

LogSense pipeline — Drain clustering surfaces error templates; Claude generates plain-language RCA with concrete next actions
Brief

LogSense ingests raw application logs (Spring Boot, Nginx, JSON, syslog), clusters similar errors using the Drain template-extraction algorithm, assigns a composite risk score to each cluster, and calls Claude (Anthropic SDK) to generate a plain-language root cause hypothesis with a concrete next action. Results surface as structured GitHub issues, Jira payloads, or live tool responses inside Claude Desktop / Claude Code via an MCP server — enabling an AI agent to diagnose and escalate incidents autonomously. Built as a legally-clean, public demonstration of the production log-mining and LLM-RCA patterns applied at Mastercard scale.

LogSense — Engineering Decisions & Key Insights
LLM Prompt Design  ·  Confidence Scoring  ·  AI-Native Architecture  ·  MCP Protocol
MCP Tool Interface
  • ingest_logs — accepts raw log content (any supported format); returns parsed + normalized entries and initial Drain-clustered templates stored to SQLite.
  • get_clusters — returns error clusters ranked by composite risk score; supports min_risk_score filter for triage focus.
  • get_rca_for_cluster — triggers LLM call for a specific cluster; returns hypothesis, confidence score (0–1), and recommended next action.
  • draft_incident_report — builds a GitHub issue body or Jira payload in dry-run mode; one config flag to ship real tickets.
Key Engineering Decisions
  • Drain over embeddings for clustering (ADR-0001) — Drain extracts log templates deterministically in linear time. Embedding-based clustering adds LLM latency and cost to every ingest call; Drain reserves the LLM budget for the high-value RCA step where it earns its keep.
  • Calibrated confidence scoring (ADR-0002) — the LLM prompt asks for an explicit 0–1 confidence float before the hypothesis text, not as a second "grader" call. Single-pass JSON output keeps latency low and makes confidence a first-class assertable field in tests.
  • MCP as primary interface (ADR-0003) — a REST API is easy to build but forces callers to orchestrate multi-step workflows manually. Exposing the pipeline as MCP tools lets Claude Desktop or Claude Code drive the full ingest → triage → RCA → draft-issue workflow in a single conversation turn, with no glue code.
  • SQLite with WAL mode — zero-config storage that supports concurrent reads without blocking writes; one environment variable switches to PostgreSQL for multi-instance deployments.
Key Insights
  • Drain clustering reduced LLM token spend by treating template extraction as a deterministic pre-processing step — only scored clusters (not every raw log line) ever reach the Anthropic API.
  • Confidence-based routing mirrors the production pattern at Mastercard (SENTINEL agent): high-confidence findings auto-escalate to Jira; low-confidence findings surface for human review — keeping the system trustworthy at scale.
  • MCP-first design means the same tool can be wired into any MCP-compatible client (Claude Desktop, Claude Code, future VS Code extension) without changing the server code.
  • The project is explicitly built to be read by engineers — the ADRs explain not just what was chosen, but what was rejected and why, demonstrating production-level engineering judgment.

TxSentry scoring engine — rule-based (70%) + statistical (30%) composite, every decision fully explained
Brief

TxSentry is a FastAPI service that ingests financial transactions — individually or as batch CSV uploads — and scores each for anomalous behavior using a rule-based + statistical composite scorer. Every score ships with a full explanation object: which rules fired, what the statistical anomaly score was, and what drove the final risk tier. The system is fully instrumented with five custom Prometheus business metrics (beyond generic HTTP stats) and a provisioned Grafana dashboard, demonstrating that production-grade observability means tracking the fraud picture, not just server health.

TxSentry — Observability & Engineering Decisions
Business Metrics  ·  Explainability  ·  Alerting  ·  API Design
Observability — Business-Level Prometheus Metrics
  • txsentry_transactions_scored_total{risk_tier, mode} — risk tier distribution over time, batch vs. stream split; a sustained HIGH-tier spike triggers PagerDuty.
  • txsentry_rule_triggers_total{rule_name} — per-rule firing rate; an impossible_travel spike often means bad upstream geo data, not actual fraud.
  • txsentry_scoring_latency_seconds — scoring engine latency excluding DB I/O; regression detector for algorithmic changes.
  • txsentry_risk_score — full risk score distribution histogram; a baseline shift signals data drift.
  • txsentry_batch_failed_rows_total — data quality signal for the CSV ingestion pipeline.

Every score ships with a full explanation object — auditable, testable, regulatorily traceable
Key Engineering Decisions
  • Statistical over ML for v1 (ADR-0001) — z-score + IQR is explainable by regulators, needs no training data, and degrades gracefully for new accounts with thin history. ML upgrade path (Isolation Forest → sequence models) documented for v2.
  • Inline explanation audit log (ADR-0002) — the explanation object is produced by the same code path that computes the score, not a separate "explainer" model. This eliminates explanation drift and makes every rule decision assertion-safe in unit tests.
  • Custom business metrics over generic HTTP metrics — generic server metrics (HTTP 200/500, latency) tell you the server is alive. Business metrics (risk tier distribution, rule trigger rates) tell you whether the fraud picture is changing.
  • Per-account statistical baselines — global z-score thresholds would flag anyone who naturally transacts in large amounts. Per-account history makes the scorer adaptive and reduces false positives without sacrificing recall.
Key Insights
  • Transaction monitoring systems are judged on explainability as much as accuracy — every HIGH-risk alert that can't be explained to an analyst is a wasted escalation. The explanation object makes TxSentry audit-ready.
  • A rule_name=impossible_travel Prometheus spike that correlates with no HIGH-risk tier increase is a data quality signal, not a fraud signal — illustrating why business metrics outperform generic HTTP dashboards for operational intelligence.
  • The zero-config SQLite → one-env-var PostgreSQL upgrade path makes the project trivially runnable locally while demonstrating production-readiness awareness.
